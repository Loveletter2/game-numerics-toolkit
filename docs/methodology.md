## 1. 乘区结构决定了配装策略

### 1.1 连乘意味着什么

绝大多数现代动作 RPG 的伤害公式是若干独立乘区的乘积：

```
D = Z₁ · Z₂ · … · Zₙ
```

对某一个乘区施加一个绝对值增量 `δ`：

```
D' / D = (Zᵢ + δ) / Zᵢ = 1 + δ / Zᵢ
```

**相对收益只取决于 `δ / Zᵢ`。** 分子是投进去多少，分母是这个区现在多大。

这条式子的三个推论：

1. 同一个区越堆越不值钱（`Zᵢ` 变大，`δ/Zᵢ` 变小）——**稀释**
2. 同样一份投入，投进小的区比投进大的区赚——**这就是所有配装攻略的唯一原理**
3. 如果不同区的「每点效率」不一样，最优解不是均分——见第 2 节

### 1.2 加算与乘算

「同一个区内加算、跨区乘算」是这套结构的关键。

- 区内加算（两条 `+10% 增伤` 相加成 `+20%`）→ 必然稀释
- 跨区乘算（`+10% 增伤` 与 `+10% 攻击` 相乘）→ 不稀释

所以设计者调平衡时，最省力的手段是**新开一个乘区**：它不与任何旧区稀释，加多少就是多少，而且不会污染旧角色的数值。乘区越多，可调旋钮越多，强度越可控。

### 1.3 为什么「对数归因」要谨慎

`ln D = Σ ln Zᵢ` 让连乘变成加法，看起来很适合做贡献度分解。但要注意：

一个数值为 1200 的攻击区和一个数值为 1.6 的暴击区，在 log 空间的占比天差地别（`ln 1200 ≈ 7.09` vs `ln 1.6 ≈ 0.47`），**但两者对伤害的"必要性"是一样的**——任何一个归零，伤害都是零。

所以 `DamageModel.log_share()` 的正确用法是「看量级分布」，不是「看谁贡献大」。**做决策要用 `marginal_table()`**，它回答的是「下一份资源投哪里」，那才是有行动含义的问题。

## 2. 最优分配：拉格朗日推导

**问题**：预算 `B` 点，每点投进第 `i` 区带来 `eᵢ` 的数值增量，怎么分？

```
max   Σ ln(Zᵢ + eᵢ·pᵢ)
s.t.  Σ pᵢ = B,  pᵢ ≥ 0
```

拉格朗日条件：

```
eᵢ / (Zᵢ + eᵢ·pᵢ) = λ
```

整理得：

```
Zᵢ + eᵢ·pᵢ = eᵢ / λ          (★)
```

**职业含义**：最优时，每个乘区的**最终数值与它的每点效率成正比**。

- 若所有 `eᵢ` 相等 → 所有 `Zᵢ` 被拉到相等 → **这就是"均衡堆"的严格含义**
- 若某区每点效率更高 → 它应该被堆得更高

### 求解

令 `t = 1/λ`，由 (★) 得 `pᵢ = t − Zᵢ/eᵢ`，且只保留正值（不能倒扣）：

```
pᵢ(t) = max(0, t − Zᵢ/eᵢ)
```

`t` 由预算约束 `Σ pᵢ(t) = B` 唯一确定，且左端关于 `t` 单调递增，**二分即可**。这正是 `allocate.optimal_allocation()` 的实现。

那些 `Zᵢ/eᵢ` 已经大于 `t` 的区，会得到 0——它们"已经堆太多了"。这个现象叫 **active set**，是水填充法的标准处理。

### 交叉验证

`allocate.greedy_allocation()` 用完全不同的思路：每一步把 1 个点投到当前边际收益最高的区。由于每个区的边际收益递减（`e/(Z+ep)` 关于 `p` 递减），**贪心对这个问题是最优的**。

两条独立路径给出相同结果，这是最好的单元测试。

## 3. 保底期望：尾和公式

对取值为正整数的随机变量 `N`：

```
E[N] = Σ_{k≥0} P(N > k)
```

原因：`N = Σ_{k≥0} 1[N > k]`，取期望后逐项相加。

于是只要知道每一步的存活概率，期望就能精确算出来：

```
P(N > 0) = 1
P(N > k) = Π_{j=1..k} (1 − pⱼ)
```

**这就是 `gacha.analytic_expected()`**，与蒙特卡洛完全独立。

### 为什么保底会大幅压低期望

如果 `pⱼ` 恒为 `p`，期望是 `1/p`。但软保底让 `pⱼ` 在尾部急剧上升，`Π(1−pⱼ)` 迅速塌到 0——**尾部和被截断了**。

示例参数下：`1/0.006 = 166.7` 抽 vs 实际 `57.2` 抽，差 65.7%。

### 期望不是全部

`std dev = 21.12`，`p50 = 68`，`p99 = 75`。

中位数（68）远高于期望（57.2）——因为分布严重左偏（少数人很早就出了）。**玩家对卡池的体感接近中位数，而不是期望。** 这是数值设计里「数学正确但体验不对」的经典陷阱。

## 4. 成长曲线的分类学

判断一条曲线的"手感"，看**每级增量**，不看终值。

定义增量比：

```
increment_ratio = 末级增量 / 首级增量
```

| 比值 | 形状 | 玩家感受 | 风险 |
|---|---|---|---|
| ≈ 1 | 线性 | 每级一样，**没有成长感** | 前中期平淡 |
| ≫ 1 | 指数 | 后期起飞 | **数值膨胀**，旧内容作废 |
| < 1 | 分段 / 对数 | 前期爽、后期稳 | 后期缺乏动力，需要靠装备/命座补 |

**分段曲线是通用解**：用前期的高增量换成长感，用后期的低增量控膨胀，终值还可以压低。示例中前 39 级每级 +18，之后每级 +5，增量比 0.28。

## 5. 为什么表必须带结论

一张排名表只是数据。要做决策，还需要三样东西：

1. **相对基准**——`% of best`。`+12% 领先第二名` 是决策依据，`18,432 点伤害` 不是。
2. **逐行诊断**——每一行标注「下一份资源该投哪里」。这样表格回答的是「我该怎么改」，而不只是「我现在是多少」。
3. **一句话结论**——把表读回成人话。`在 67% 的方案里，最值得补的都是攻击区` 才是能写进报告的东西。

第 3 点是 `builds.insights()` 存在的理由。它统计的是**所有方案共同的短板**，而不是最优方案本身——因为共同短板才是这个角色/这套体系的结构性问题。

### 枚举的边界

笛卡尔积会爆炸。10 个乘区各 5 个候选值是 976 万种组合，跑不完也没人看得完。

所以工具设了默认上限（20000），超过直接报错并提示收窄。**这是刻意的**：一张 20000 行的表没有决策价值，有用的表通常在 50—500 行之间。
