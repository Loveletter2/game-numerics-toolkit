# 校验日志：我怎么发现自己的表是错的

配装表的数值来自测试服。测试服到正式服之间，倍率会改、段数会改、机制会重构。
这篇文章记录三次发现问题、定位问题、并确认修正的过程。

写下来的理由很简单：**模型看起来对，和模型真的对，是两件事。**
而这两件事之间的差距，只有拿外部锚点去撞才能发现。

---

## 案例一：0.26% 的防御偏移

**现象**：防御系数用的是社区常见的对称形式——

```
(己方等级 + 100) / ((己方等级 + 100) + (敌方等级 + 100))
```

看起来非常合理：双方都 +100，公平。

**撞锚点**：去查敌人属性表，90 级敌人的防御不是 1520，而是 **1512**。

```
1512 = 8 × 189          （不是 8 × 190）
```

拆开看就清楚了：己方那一侧的常数是 `K = 800 + 8×等级 = 8×(等级+100)`，
而敌方那一侧的防御值是 `8×(等级+99)`。**两边都带因子 8，所以 8 约掉了**，
剩下的是 `+100` 对 `+99` —— 并不对称。

**结论**：

```
防御系数 = (己+100) / ((己+100) + (敌+99))
```

原来写的是 `190/389 = 0.4884`，正确的是 `190/388 = 0.4897`，**差 0.26%**。

**为什么值得记**：这个偏差不影响任何配装排序（它是全流程共用的常数因子），
所以「我的表很准」和「我的公式错了」可以同时成立。
**只有和外部锚点对，才会暴露。**

## 案例二：大招的段数 7 → 8

**现象**：大招倍率写成 `69.59% × 7 段 + 208.76%`，总和 6.9589。

**碰运气的发现**：拿官方数据核对总倍率——对得上，差 0.00%。
几乎就放过这条了。

但顺手看了一眼原始写法：

```
官方：60.89% × 8 段 + 208.76% = 6.9588
表内：69.59% × 7 段 + 208.76% = 6.9589
```

**总倍率一样，段数不一样。**

**为什么要改**：期望值一样不代表模型一样。段数影响两件事——

1. **取整**：每段独立 `CEILING(...,1)`，8 段比 7 段多一次向上取整
2. **方差**：段数越多，暴击越接近期望

如果模型只输出期望值，这个错误永远不显现。但只要做「下限」「最坏情况」
「稳定性」分析，段数就是决定性参数。

## 案例三：21 段 vs 2 段——期望一样，方差差一个量级

**现象**：被动飞镖写成 `11.37% × 21 段`，总和 2.3877。

**核对结果**：官方数据是 `119.36% × 2 段`，总和 2.3872，**差 0.02%**。

总伤害几乎完全相同，但结构完全不同：

| | 21 段 × 11.37% | 2 段 × 119.36% |
|---|---|---|
| 期望 | 2.3877 | 2.3872 |
| 每段占总量 | 4.8% | 50% |
| 暴击波动 | 几乎必然贴近期望 | 大幅波动 |
| 取整累积 | 21 次 | 2 次 |

**这条最能说明问题**：如果只比总倍率，两个写法等价；但从「这个角色输出稳不稳」
的角度看，它们是两种完全不同的角色。

---

## 方法论：怎么找锚点

三次都是同一个流程：

1. **找一份独立来源**（官方数据 / 另一份社区表 / 实测录屏）
2. **对齐口径**（技能等级、敌人等级、是否含段数）
3. **比同一层的数**，不要比最终伤害——最终伤害会被十几个乘区混在一起，什么都看不出来
4. **差异 < 1% 也要追**：常数级的小偏差，通常指向一个写错的常量

第 4 条是最反直觉的。**大偏差容易发现，因为它会错得很明显；
小偏差才危险，因为模型会带着它一直自洽下去。**

---

## 顺带：口径本身就是坑

对齐口径比对齐数值更难。这三次核对里踩到的口径问题：

- 官方数据的倍率是**字符串**（`24.50%`、`10.85%*4`），段数写在字符串里
- 社区表是**万分之一精度的整数**（`2450`），段数在另一个独立列
- 技能等级 1 和 10 的倍率差接近 2 倍，对不上 99% 是等级没对齐，不是数据错了

**先确认口径，再比数值。** 否则会在错误的对齐上浪费大量时间。
